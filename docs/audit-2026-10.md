# Audit de code ffs2play — octobre 2026

Base auditée : `devel` après la release 2.4.0 (Qt 6.12, C++17, ~18 500 lignes hors build).
Axes : sûreté multi-thread, passage au standard C++20, propriété mémoire et remplacement des pointeurs bruts par des
références. Les corrections sont faites sur la branche `feature/audit-cpp20`, une étape par commit ; la colonne
« État » est mise à jour au fil des commits.

Gravité : **C** critique (UB / crash possible), **M** majeure (bug fonctionnel ou fuite), **m** mineure (qualité).

## 1. Modèle de threads

| Thread | Rôle | Objets concernés |
|---|---|---|
| GUI (principal) | interface, P2P (UDP/TCP), portail web, UPnP, timers, slots de tous les QObject | tout sauf ci-dessous |
| Boucle simulateur | `simbasemanager::mainThread()` appelle `SimConnector::main_loop()` en boucle | `CSCManager` (SimConnect_CallDispatch) ; vide pour X-Plane et FlightGear |
| Scan IA | `AIBaseParser::scanSimObject()` parcourt les dossiers d'avions et met à jour SQLite | `SCAIParser`, `XPAIParser`, `XPCSLParser`, `FGAIParser` |

Les deux threads secondaires exécutent des méthodes d'objets qui **vivent dans le thread GUI** (slot branché en
`Qt::DirectConnection` sur `QThread::started`). Les signaux qu'ils émettent sont donc remis en file vers le thread GUI
(correct), mais toutes les données membres sont partagées avec le thread GUI sans règle de synchronisation claire.

## 2. Constats — concurrence

**Correctif retenu pour T1 à T8 (étape 2)** : le thread de la boucle simulateur ne servait qu'à SimConnect.
`SimConnect_Open` reçoit maintenant un événement Windows, surveillé par un `QWinEventNotifier` qui lit les messages
(`SimConnect_GetNextDispatch`) dans le thread GUI. Il n'y a plus de thread simulateur : connecteurs et
`simbasemanager` ne sont plus partagés entre threads (mutex des connecteurs retirés), plus de boucle active
(CPU au repos ≈ 0), et `close()` libère aussi une connexion encore en attente de réponse du simulateur.

### Étude : remplacer les pointeurs par des références

- **Singletons** (`CLogger`, `simbasemanager`, `CWebManager`, `CP2PManager`, `AIMapping`, `Analyzer`, `CTheme`) : 54 appels
  `X::instance()` dont le résultat est rangé dans une quarantaine de membres `CLogger* m_log`, `simbasemanager* m_simManager`…
  Ces pointeurs ne sont **jamais nuls** et ne sont **jamais réaffectés** : ce sont des références déguisées. On fait
  renvoyer `T&` à `Singleton<T>::instance()` et aux `X::instance()`, et les membres deviennent des références (`CLogger& m_log`).
  Les tests `!= nullptr` sur ces objets disparaissent. Ces classes étant des QObject non copiables, perdre l'affectation ne coûte rien.
- **Paramètres** : les objets obligatoires passés par pointeur deviennent `T&` / `const T&`.
- **À garder en pointeur** :
  - enfants QObject créés avec un parent (`new UDPServer(this)`, sockets, `CHttpRequest`) : c'est le modèle de propriété de Qt.
    Quand leur durée de vie est celle du parent, on peut en faire des membres par valeur ;
  - pointeurs réellement optionnels (`CPeer::m_TCPClient`, `DialogProfils::m_currentProfil`), éventuellement en `QPointer` ;
  - pointeurs renvoyés par Qt (`QListWidgetItem*`, `QAction*`…).
- **Réalisé (étape 6)** : `Singleton<T>::instance()` et les 7 `X::instance()` renvoient `T&` ; 39 membres (18 classes)
  sont devenus des références initialisées dans leur déclaration (`CLogger& m_log = CLogger::instance();`), les
  appels `X::instance()->` sont devenus `X::instance().`.
  **Exception volontaire : `MainWindow`** garde des pointeurs (sauf `m_log`) affectés dans le corps du constructeur,
  car l'ordre de création des singletons y est significatif : la fenêtre s'abonne au journal *avant* de créer
  `simbasemanager`, dont la construction écrit déjà dans le journal (chargement du module simulateur). Un membre
  référence étant lié avant le corps du constructeur, ces messages seraient perdus.
- Les références ne rendent pas le code thread-safe : elles suppriment une classe de bugs (pointeur nul ou pendant après
  réaffectation) et rendent l'intention explicite. La sûreté de durée de vie vient de `std::unique_ptr` et de l'arrêt
  propre des threads (T2, T4, T10).

## 5. Ce qui ne change pas

Aucun format réseau ni contrat n'est touché (protobuf, protocole X-Plane, P2P, API du portail) : pas de fiche
`docs/changes/`, compatibilité avec les clients 2.3.x et le plugin inchangée. Les chaînes `tr()` restent à l'identique.
